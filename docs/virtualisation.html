7.2.2 Pytania

O co chodzi z plikami konfiguracyjnymi pod pod. Przeciez powinnismy pracowac tylko na warstwie Deployment/StatefulSet, a mimo to pods sie pojawialy (np w przykladzie przy konfiguracji Volumens pod pods). Pods maja chyba dynamicznie nadawane nazwy (przynajmniej te stateless) z hashami. Jak się do takich nazw odwolywac w tych plikach? Pods maja tez dynamiczne adresy IP, ale ten problem rozwiazuje Services.

Jak wyglada komunikacja sieciowa (nie przez Volume) miedzy contenerami w pod? Chyba jest jakies rozwiazanie provider-consumer, bo same kontenery nie maja adresu IP (ma je pod). Nie wiem czy poza Volumes da sie (albo czy jest zalecane) komunikowanie sie kotenerow miedzy roznymi pod-ami (np. sieciowo). Chyba sie da poprzez Services (patrz podrozdzial o Services).

Komunikacja miedzy kontenerami: link

What is kunernetes context : A kubernetes context is just a set of access parameters that contains a Kubernetes cluster, a user, and a namespace. kubernetes Context is essentially the configuration that you use to access a particular cluster & namespace with a user account

What is Job: A Job creates one or more Pods and will continue to retry execution of the Pods until a specified number of them successfully terminate. As pods successfully complete, the Job tracks the successful completions. When a specified number of successful completions is reached, the task (ie, Job) is complete. Deleting a Job will clean up the Pods it created. Suspending a Job will delete its active Pods until the Job is resumed again.

7.2.3 Rozne uwagi

  • Kubernetes moze miec pod soba rozne rozwiazania kontenerowe. Wiec nie koniecznie musi to byc Docker.

  • Na kontenerach jest budowana dodatkowo Kubernetosewa warstwa Pod. Umożliwia ona abstrakcje kontenerow. Dzieki temu pracujac z kontenerami mozemy byc caly czas w warstwach Kubernetesa nie schodzac do samych kontenerow. Tak naprawdę w praktyce nie schodzi się nawet do warstwy pod, ale pracuje z poziomem Deployment. Teoretycznie jeden pod moze miec pod soba kilka kontenerow, ale sie rzadko sie tego uzywa.

  • Kubernetes obsuguje Volume ktore tak jak przy dockerach sluza do przechywywania w sposob trwaly informacji. Kubernetes domyslnie nie zarzadza Volumnes. Volumes moga byc lokalnie w klastrze (ktorys z Nodow), albo byc zdalne. W obu przypadkach sa one plug-inem do calego Kubernetesa i znajduja sie poza samym Kuberneteresm. W przypadku baz danych zaleca sie aby byly one zdalne. Po pierwsze nasz VOlumne jest niezalezy od problemow z Nodami, a po drugie nie jest zwiazany z konkretnym Nodem (to chyba generuje np. utrudnienie w konfigurowaniu polaczen do Volume). Dodatkowo wystepuja jeszcze volumes wewnatrz pod-a do komunikacji miedzy kontenerami. Ale te volume zyja tak dluzo jak zyje pod.

  • Ingress - Interfejs zewnetrzny umozliwiajacy komunikacje aplikacji ze swiatem zewnetrznym. Mozna to pominac poprzed odpowiednio skonfigurowane Service, ale jest to rozwiazanie zalecane.

  • Services - wiece - patrz podrozdzial o tym temacie.

  • ConfigMap - trzyma rozne konfiguracje. Jezeli cos zmieniamy w calym systemie, to zamiast robic to na poziomie poszczegolnych kontenerow, mozna tym zarzadzac przez taki plik. Technicznie jest to szczegolny przypadek Volume.

  • Secret. -Taki ConfigMap, ale uzywany do przechowywanie hasel i innych poufnych informacji. Technicznie jest to szczegolny przypadek Volume.

  • Deployment - Replikacje i wiele innych rzeczy związanych z zarządzaniem robi się nie ręcznie, ale przez Deplyment. Uwaga. Przez Deployment nie mozna duplikowac baz danych. Duplikaty baz korzystaja z tych samych Volumes i trzeba zapewnic ze zapisy z roznych duplikatow baz nie doprowadza do niezgodnosci w danych. Do tego uzywa sie Statefulset. Poza Deployment jest jeszcze warstwa replicaset ktora jest pod nia, ale jest powyzej warstwy pod. Sluzy do zarzadzania replikami pod-ow. Zarzadzmy ta warstwa z poziomu deployment.

  • Statefulset - Przez Deployment nie mozna duplikowac baz danych. Duplikaty baz korzystaja z tych samych Volumes i trzeba zapewnic ze zapisy z roznych duplikatow baz nie doprowadza do niezgodnosci w danych. Do tego uzywa sie Statefulset.

7.2.4 Architektura

Mamy master node i workes nodes.

Na kazdym worker node musza byc zainstalowane 3 komponenty:

  • Container runtime - narzedzie do uruchamiania kontenerow (np. Docker Engine)

  • Kublet - interfejs Kubernetersa do wspolpracy z Container runtime i z samym nodem.

  • Kube proxy. Narzedzie do optymalizacji pracy pod katem przeplywu informacji. Chodzi o to zeby minimalizowac ruch sieciowy. Np. jezeli dwa kontenery (a wlasciwie pod-y) musza sie ze soba skomunikować to niech to bedzie w ramach tego samego Noda jezeli to jest mozliwe. Kube proxy umozliwia rozniez komunikacje pod-ow ze swiatem zewnetrznym

Na master node mamy 4 komponenty:

  • API Server - interfejs dla użytkownika do zarzadzania interfejsem. Rowniez waliduje request-y uzytkownikow.

  • Scheduler - Np. jezeli chcemy utworzyc nowy Pod, to po weryfikacji naszego requesta przez API Server, to scheduler zadecyduje na jakim node go utworzyc. Zbada gdzie sa odpowiednie zasoby dla naszej aplikacji. (po wybraniu lokalizacji samego pod-a zalozy nam na nadzie Kublet)

  • Controller Manager - wykrywa stany pod-ow (np. ich zawieszenie się, albo wywalenie się). Jezeli jest problem (np. pod sie zawiesi) to Controller Manager sprobuje go zrestartowac. W celu optymalizacji wspolpracuje ze schedulerem, ktory samo zadanie (czyli np. restart pod-a) zleca Kublet-owi.

  • etcs - klucze z zapisanymi informacjami o stanie klastra Kubernetesowego. Czyli wszystkie operacje klustra (glownie zwiazane z pod) sa tu rejestrowane. Scheduler i Controller Manager* korzystaja z niego. Na jest podstawie wiedza co gdzie jest na nod-ach.

7.2.4.1 Podzial pod-ow na aplikacje stateful i stateless

  • sateful pods - potrzebuje zapisywania informacji o swoich stanach rzeczy sie do nich potem odwolywac. Przykladem jest baza danych. W Kubernetes sa obslugiwane przez Deployment. Nie mylic ich z Volumes.

  • stateless pods - nie musza zapisywac inforamcji o swoim stanie ich pamietac. W Kubernetes sa obslugiwane przez StatefulSet.

Dla sateful jest duzo trudniej robie replikacje, bo sa dodatkowe wymagania. Tutaj kazdy replikowany pod ma swoj oddzielny identyfikator.

W stateless pods mamy podzial na mastera i workerow:

Kazdy element ma swoje oddzielne pv (volumne). Kiedy nastepuje zmiana w danych na Master , to wtedy obowiazkiem Workerow jest synchronizacja danych z Masterem tak aby wszedzie byly te same dane.

Uwaga. Volumnes nie sa obowiazkowe, ale robienie bazy bez Volumes nie ma sensu. W komencie restartu pod-a utracimy dane.

Nazewnicto dla stateful pods to nie sa losowe hashe (jak w statless), ale narastajace numery.

numer 0 (zero) to zawsze master. Kolejny workes jest tworzony na podstawie poprzedniedo (np. 3 odwoluje sie do 2). Jak usuwamy np. 3 to wczesniej musimy usunac wyzsze numery ( w kolejnosci od najwyzszego numeru).

Nazwy pod-to dla stateful sa tez stale (dla stateles przy restarcie pod-a hash jest chyba generowany na nowo). Dzieli czemu po restarcie nod-a mozna np. latwo przywrocic jego podpiecie do pv (hmm, stateless nie ma sztywnego polaczenia z pv?)

Kuberneter dosys slabo wspiera te wszyskie procesy zwiazane z stateful. Np. synchronizacje danych musimy sobie sami ogarnac.

typy Service:

ClusterIP:

  • jest domyslny

  • jest wewnetrzny w tym sensie ze nie wystawia komunikacji poza Kluster Kubernetesa.

  • pods maja zmienne adresy IP, natomiast Service ma staly adres. Dzieki czemy w komunikacji lepiej odwolywac sie do service ktory na przekieruje na pod niz do samych pod.

  • Zduplikowane pod-sy sa podpinane automatycznie pod ten sam services (jezeli oczywiscie poda podpielismy pod Service).

  • Uzywa sie ich do podpinania pods z aplikacjami stateless

Headless:

  • Uzywa sie ich do podpinania pods z aplikacjami statefull. W ClusterIP kiedy mamy duplikaty pod podpietych pod to samo ip service , to ten service losowo nas przekierowuje do ktorejs z kopii. NodePort:

  • Sa przypisane do Nod-a, ale tak jak ClusterIP moga przekierowywac na pods.

  • Maja mozliwosc bezposredniej komunikacji ze swiatem zewnetrznym (bez posrednictwa Ingress) co nie jest do konca dobre.

  • W praktyce sie bardzo rzadko je stosuje.

  • Traktuje sie je jako rozwiniecie ClusterIP.

LoadBalancer Services

  • To rozwiniecie NodePort umozliwiajace komunikacje ze swiatem zewnetrznym (bez posrednictwa Ingress) poprzez LoadBalancer.

  • Aby uzyskac ten typ:

    type:LoadBalancer

    oraz w portach dodajemy port noda. Port noda w przeciwienstwie do NodePort nie jest wystawiony bezposrednio na zewnatrz.

7.3.6.2 attach vs exec

Attach:

Po prostu umozliwia nam podpiecie sie terminalem pod kontener i tym samym prace z nim w inteaktywnym trybie (przez ten terminal).

Exec:

Docker exec executes a new command / create a new process in the container’s environmen.

Ponizsze uzycie exec daje podobny efekt co attach (-it od interactive terminal)

sudo docker exec -it <caontainer_name> /bin/bash

7.3.8.4.1 Bindowanie katalogow

Mozemy je skomunikowac ze swiatem zewnetrznym poprzez spiecie katalogu dockera z katalogiem na hoscie (Volumes):

Sa 3 rodzaje Volumes:

  • Host volumnes (Bind mount): reczne mapowanie katalogu z hosta na katalog z kontenera

  • Anonymous volumes: okreslam katalog w kontenerze, a na hoscie automatycznie docker robi sobie swoja lokalizacje (nie jest ona chyba bezposrednio dostepna. Docker sam sobie tym zarzadza).

  • Named volumnes: to co powyzej, ale dodatkowo okreslam nazwe, do ktorej moge sie potem odnosic (zalecany sposob pracy z Volume). Nazwa odnosci sie do folderu na hoscie.

Anonymous volues i named volumes sa zazwyczaj domyslnie tworzone w takich lokalizacjach:

W tych katalogach kazdy volumen na swoj indywidualny hash.

Volumes to byty niezalezne od kontenerow. Usuwajac kontener nie usuwamy razem z nim automatycznie volume.

Polecenia

# lista volumes
docker volume ls

# lista filtrowana po nazwie volumne
docker volume ls -f name=data

# inspecja
docker volume inspect <nazwa_volume>
  
  
# usuwanie
docker volume rm <nazwa_volume>
  
  
# usuwanie volumow nie uzywanych (nie spietych z zadnym kontenerem)
docker volume prune


# utworzenie volume nie podpietego pod kontener (named volume)
docker volume create <nazwa_volume>

# podpiecie istaniejacego volume pod kontener
docker run --mount source=[volume_name],destination=[path_in_container] [docker_image]


# utworzenie volumen typu host volume przez polecenie run (mount point jest tutaj w pwd)
docker run -v $(pwd):/var/opt/project <image_name>
  

# podpiecie kontenera do voluma innego kontenera
docker run --volumes-from <nazwa_kontera_do_volume_ktore_sie_podpinamy> <nazwa_obrazu>

W ramach volume mountpoint dotyczy katalogu po stronie hosta a nie kontenera.
